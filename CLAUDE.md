# Orqenta Project Documentation

## Overview

**Orqenta** is a modern invoicing application for small teams. It provides customers, products, tax rules, invoicing, and e-invoice export in UBL 2.1 XML format.

- **Status**: Active development
- **Tech Stack**: Next.js 16 (App Router), React 19, TypeScript, Drizzle ORM, PostgreSQL, Tailwind CSS
- **Runtime**: Node 22+, pnpm 11+, Docker
- **Port**: `3001` (dev server), `5433` (PostgreSQL in Docker)

## Architecture

### Core Design Principles

1. **Server-first data layer**: All data access goes through Next.js server actions only — no REST API, no route handlers for data mutations.
2. **Business logic isolation**: All business rules live in `src/lib`, away from both React and the database. This layer is fully tested.
3. **Explicit error handling**: Server actions return `ActionResult<T>` (success or failure) instead of throwing, so error messages aren't replaced by generic production defaults.
4. **Type-safe schema**: Database types are inferred from Drizzle tables, making schema changes automatically propagate as type errors rather than runtime surprises.
5. **Shared rendering context**: One context object feeds the owner's HTML view, PDF, and public share page—they cannot disagree.

### Permission Model (§10.13)

- **Two roles**: Admin (bypasses all checks) and regular users with per-resource, per-action permissions.
- **Resources**: `invoices`, `customers`, `products`, `templates`, `settings`, `tax_definitions`, `users`
- **Actions**: `read`, `create`, `update`, `delete`, `publish`, `void`, `export`, `install`
- **Check pattern**: Every action calls `await requirePermission("resource", "action")` first.

### Data Flow

1. **Client**: React components + TanStack Query (read/write)
2. **Server Actions**: Handle permission checks, Zod validation, database calls
3. **Database**: Drizzle ORM + PostgreSQL
4. **Business Logic**: `src/lib/*` functions (money, numbering, templates, invoice status, XML)

## Key Files and Patterns

### Data Fetching Pattern (Client-Side, Using TanStack Query)

**Rules for all pages and components:**
1. **Pages are simple wrappers** — Just render components, no data fetching
2. **Components fetch their own data** — Using `useQuery` from TanStack Query
3. **Never fetch in pages** — Keep data fetching in client components where it's cached and can refetch

**Example Pattern:**

```typescript
// Page (server component): Just passes route params
export default async function InvoicePage({ params }: PageProps<"/invoices/[id]">) {
  const id = (await params).id;
  return <InvoiceDetail invoiceId={id} />;
}

// Component (client component): Fetches its own data
export function InvoiceDetail({ invoiceId }: { invoiceId: string }) {
  const { data: invoice, isPending, error } = useQuery({
    queryKey: ["invoices", invoiceId],
    queryFn: () => getInvoice(invoiceId).then(unwrap),
  });

  if (isPending) return <Skeleton className="h-96 w-full rounded-xl" />;
  if (error) return <Alert variant="destructive"><AlertTitle>Failed to load</AlertTitle></Alert>;

  return <div>{/* render invoice */}</div>;
}
```

**Benefits:**
- TanStack Query handles caching, refetching, and deduplication
- Components have loading/error UI
- Pages stay simple and focused
- Data fetching is co-located with usage
- Follows the customer, product pages pattern

### Server Actions Pattern

All server actions follow this structure:

```typescript
"use server";
import { runAction, type ActionResult } from "@/lib/action-result";
import { requirePermission } from "@/lib/auth/session";

export async function doSomething(input: Input): Promise<ActionResult<Output>> {
  return runAction(async () => {
    await requirePermission("resource", "action");
    // Validation with Zod happens here (in runAction)
    // Database call
    return result;
  });
}
```

**Key points**:
- `"use server"` directive at the top
- Wrap body in `runAction()` to handle errors consistently
- Call `requirePermission()` before database work
- Return `ActionResult<T>`, not throw (except for redirect/notFound)
- Zod errors are flattened into `{ ok: false, fieldErrors: {...} }`

### Database Schema and IDs

**ID generation**:
- Custom prefixed IDs using `generateId()`: `cus_*`, `inv_*`, `prod_*`, `usr_*`, etc.
- Reasons: Human-readable in logs, reduce UUID cardinality, easier debugging

**Timestamps**:
- All tables have `createdAt` and `updatedAt` (via helper)
- `updatedAt` auto-updates on every change

**Invoice status**:
- Never stored in the invoice row
- Derived on every read from the most recent `invoiceStatusHistory` row
- **Key insight**: An invoice stops being "overdue" the moment the due date changes (§4.5)

### Money and Rounding (§4.2–4.3)

`src/lib/money.ts` handles all decimal arithmetic:
- **Rounding modes**: `line` (round each item), `total` (round the invoice once)
- **Invariant**: Every intermediate step is rounded deliberately, so results match the legacy system cent for cent
- **Tax calculation**: Either per-line (TAX_MODE: "line") or per-invoice (TAX_MODE: "invoice")
- **Usage**: Always import and use `roundCents()`, `calculateTax()`, etc. — never raw JS arithmetic

### Invoicing Workflow

1. **Draft**: Created, items/taxes editable, no history tracking
2. **Sent**: Published, protection enabled, read-only (unless admin)
3. **Complete**: Marked finished
4. **Paid**: Status history records the payment method (§4.5)
5. **Overdue**: Derived from due date vs. today (§4.5)
6. **Voided**: Terminal state, retention-protected (§4.6)

## Database

### Migrations

Drizzle tracks migrations in `src/db/migrations/`. **Do not edit manually.**

```bash
pnpm db:generate   # After schema changes, generates a migration
pnpm db:migrate    # Applies pending migrations
pnpm db:push       # Push schema directly (dev only, no history)
```

### Seed

`src/db/seed.ts` is idempotent and safe to re-run on every deploy:
- Creates admin user (only if `users` table is empty)
- Sets up default settings
- Installs built-in invoice template
- Safe on re-runs: checks for existence before inserting

### Schema Highlights

- **Users**: `id`, `username`, `passwordHash`, `isAdmin`, `isActive`
- **Invoices**: `id`, `customerId`, `status` (derived, not stored), `issueDate`, `dueDate`, `currency`, `numberPrefix`, `numberSequence`
- **InvoiceItems**: `id`, `invoiceId`, `description`, `quantity`, `unitPrice`, `taxes` (array)
- **Customers**: `id`, `name`, `contactName`, `email`, `taxId`, `countryCode`
- **Products**: `id`, `name`, `code`, `categoryId`, `unitId`, `price`
- **Templates**: `id`, `name`, `type` ("builtin", "local", "remote"), `content` (interpolation, not evaluation)
- **Settings**: Global app settings (invoice prefix, VAT rates, etc.)

## Security Considerations

### Content Security Policy (CSP)

Defined in `next.config.ts`:
- `script-src 'self' 'unsafe-inline'` (required for RSC bootstrap)
- Dev adds `'unsafe-eval'` for React Refresh only
- `img-src` allows data: and blob: (for generated PDFs/QR codes)
- No external CDNs for scripts or styles

### Permissions & Rate Limiting

- **Permission checks**: Every action calls `requirePermission()` (§10.13)
- **Rate limiting** (login): `RATE_LIMIT_ENABLED`, `RATE_LIMIT_MAX_ATTEMPTS`, `RATE_LIMIT_WINDOW_SECONDS`
- **Session**: JWT-signed cookies, configurable TTL (300–43200 seconds)
- **Secure cookie flag**: Tied to `COOKIE_SECURE` env var (HSTS header enabled only when true)

### Database Credentials

- Stored in `.env`, never in `compose.yaml` or source code
- `.env` is in `.gitignore`
- `.env.example` shows the shape but not secrets

### Puppeteer for PDF

- Configured in `next.config.ts`: `serverExternalPackages: ["puppeteer"]`
- Reason: Puppeteer resolves Chrome binary paths at runtime; bundling it breaks those paths
- Optional: Point `PUPPETEER_EXECUTABLE_PATH` at an existing Chrome instead of bundling

## Important Notes

### Read-Only Schema Imports

Types in `src/lib/types.ts` import table definitions with `type` keyword only:

```typescript
import type { customers, invoices } from "@/db/schema/tables";
export type Customer = typeof customers.$inferSelect;
```

This ensures Drizzle schema never reaches the client bundle.

### Session User in Actions

Access the current user via:

```typescript
import { getSessionUser } from "@/lib/auth/session";
const user = await getSessionUser();
if (!user) return redirect("/login");
```

### Query Invalidation

TanStack Query cache is managed in `src/lib/query-invalidation.ts`:
- Reads invalidate at resource root (e.g., `listCustomers` invalidates on any customer write)
- Cross-resource invalidations are documented here (e.g., deleting a product invalidates invoices if items reference it)

### Share Link & Public Route

The public invoice share page (`src/app/public/`) uses a `shareToken` query param to load an invoice without authentication. No sign-up or login required.

## Contributing Guidelines

1. **Schema changes**: Modify table definitions in `src/db/schema/tables/`, run `pnpm db:generate`, commit the migration
2. **Business logic**: Add to `src/lib/*` with tests; keep it independent of React and database layer
3. **New actions**: Follow the server action pattern (wrap in `runAction`, check permissions, return `ActionResult<T>`)
4. **Type vocabulary**: Add new types to `src/lib/types.ts` or `src/lib/permissions.ts`
5. **Run tests and lint**: `pnpm test && pnpm lint` before pushing
